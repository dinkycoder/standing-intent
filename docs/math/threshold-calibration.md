# Calibration for the price-anomaly classifier

**Course:** Quantic "Mathematics for AI Engineering" -- Probability
Fundamentals & Distributions, conditional probability and Bayes' rule.
**Code:** `evals/ml/price_classifier.py`, `evals/ml/synthetic_data.py`,
`scripts/train_price_classifier.py`.
**Tests:** `tests/test_price_classifier.py`, `tests/test_synthetic_data.py`.
**Design:** `docs/superpowers/specs/2026-09-19-week7-trained-model-design.md`.

## The problem this closes

A 3-class accuracy number (65.4% on this classifier's held-out test set,
see `docs/week7-trained-model-live-run.md`) answers "how often is the top
guess right." It says nothing about whether the *probability* attached to
that guess means anything. A classifier that's right 65% of the time but
outputs `P(escalate) = 0.99` whenever it guesses escalate is badly
miscalibrated -- confident far beyond what its actual hit rate supports.
Since this classifier's whole reason for existing is to eventually feed a
*probability* into a policy decision (accept outright / escalate to a
human-legible signal / reject), not just a label, a wrong-but-confident
probability is a worse failure than a wrong label: it would make a
downstream threshold ("escalate if P > 0.4") systematically miscount how
often that threshold is actually crossed for the right reasons.

## What calibration means here, precisely

For a binary event $E$ (here, "the true label is escalate") and a model
that outputs $\hat p = P(E \mid x)$ for input $x$, the model is
**calibrated** if, among every input where the model says $\hat p$, the
event $E$ actually occurs at rate $\hat p$:

$$P(E \mid \hat p(x) = p) = p \quad \text{for every } p \in [0, 1]$$

This is a direct statement about **conditional probability** — not "is the
model's internal probability the true Bayesian posterior" (which would
require knowing the true generating process exactly), but "if you bucket
predictions by their stated confidence, does reality agree with that
bucket's stated rate." It is checkable empirically without knowing the true
model, which is exactly what `sklearn.calibration.calibration_curve` does:
bin the test set by predicted $\hat p$ (here, deciles), and for each bin
compare the mean predicted $\hat p$ against the bin's actual escalate rate.

`escalate` (not `accept` or `reject`) is the class checked, one-vs-rest,
because it's the one class with real ambiguity on both sides — an offer
near the accept/escalate boundary or the escalate/reject boundary is where
a wrong probability actually changes what a downstream policy would do.
`accept` and `reject` are the two extremes of the same underlying z-score
axis; `escalate` is the genuinely uncertain middle this whole classifier
exists to quantify.

## Why this classifier's calibration is checkable in the first place

This is worth being explicit about, because it's not automatic. This
classifier's training data (`evals/ml/synthetic_data.py`) is not labeled by
a hard rule -- it is generated by literally sampling from a known logistic
function of a price's z-score within its category:

$$P(\text{label} = \ell \mid z) = \frac{e^{\eta_\ell(z)}}{\sum_{\ell'} e^{\eta_{\ell'}(z)}}, \qquad \eta_\ell(z) = a_\ell + b_\ell z$$

with `accept` pinned at $\eta = 0$ and `escalate`/`reject` each a linear
function of $z$ (see the design spec's "Scope decisions," #4). Because the
*true* generating process is exactly a multinomial logistic function of $z$,
and `LogisticRegression` fits exactly that functional form, there is a real
question to ask: does the *fitted* model's $\hat p(z)$ recover the *true*
generating $P(\text{escalate} \mid z)$? A classifier trained on data with a
hard, deterministic label rule couldn't be checked this way -- every
correctly-classified point would trivially look "calibrated" at probability
1, with no genuine test of whether the probability *number* means anything.

## The actual result

From the live run (`n=5000, seed=42`, see
`docs/week7-trained-model-live-run.md` for the full report):

| predicted P(escalate) | empirical rate | difference |
|---:|---:|---:|
| 0.115 | 0.110 | −0.005 |
| 0.198 | 0.150 | −0.048 |
| 0.251 | 0.250 | −0.001 |
| 0.301 | 0.270 | −0.031 |
| 0.351 | 0.400 | +0.049 |
| 0.400 | 0.470 | +0.070 |
| 0.448 | 0.390 | −0.058 |
| 0.485 | 0.510 | +0.025 |
| 0.520 | 0.530 | +0.010 |
| 0.550 | 0.520 | −0.030 |

The largest gap is 7 points (predicted 0.400 vs. empirical 0.470), on a
decile bin holding roughly 100 test points -- well within sampling noise
for that bin size (a 100-point binomial sample's own standard error at
$p\approx0.45$ is about 5 points). The lower and upper deciles (where most
of the test set's mass actually sits, since `accept` dominates the overall
label distribution) track within 1-5 points. **This classifier is
well-calibrated for its "escalate" probability** -- not because calibration
was optimized for directly (`LogisticRegression`'s default fit is a
maximum-likelihood fit, not a calibration-specific objective), but because
the model class matches the true generating process closely enough that
good likelihood fit and good calibration coincide here. That coincidence is
specific to this synthetic setup (see the design spec's "Known
limitations") and is not a claim that any classifier trained this way would
calibrate this well.

## The other half of Bayes' rule this week: vendor reliability

`evals/ml/reliability.py`'s Beta-Binomial tracker is the other place Bayes'
rule does real work in this week's PR, in the classical sequential-updating
form rather than the calibration-checking form above. A vendor's
reliability is modeled as an unknown success probability $\theta$ with a
uniform prior, $\theta \sim \text{Beta}(1, 1)$. Each observed settlement
(`ExecutedPurchase.verified`) is one Bernoulli trial; by Bayes' rule, the
Beta prior is conjugate to the Bernoulli/Binomial likelihood, so the
posterior after $s$ successes and $f$ failures is exactly

$$\theta \mid s, f \;\sim\; \text{Beta}(1 + s,\; 1 + f)$$

with posterior mean $\frac{1+s}{2+s+f}$ — no numerical inference needed,
the update is the closed-form increment `beta_update()` performs. The live
run's real numbers (`wx_alpha`: 8 observations, mean 0.900; `wx_bravo`: 24
observations, mean 0.962 — see `docs/week7-trained-model-live-run.md`)
are this exact posterior, not an approximation to it.

## What's still open

- Calibration was checked only for the `escalate` class, one-vs-rest, at
  one train/test split. Whether `accept` and `reject` are individually
  well-calibrated (not just correctly ordered relative to each other) was
  not separately checked here.
- The near-collinearity among this classifier's four input features (three
  of the four are affine functions of the price z-score within a category,
  by construction of the data generator -- see the Week 7 final review's
  Minor finding #7) means this specific calibration result says less about
  "does calibration survive genuinely independent features" than a richer
  feature set would. That's a property of today's synthetic data, not of
  calibration checking generally.
- The vendor-reliability posterior's real numbers today reflect
  `SyntheticExecutor`'s near-zero failure rate, not real-world vendor
  behavior -- see the design spec's Known limitations for why that's
  expected, not a result being overclaimed.
